what steps should i take to enable Internet on the smartnic?

Below is a clean, end-to-end checklist to enable Internet access on a SmartNIC / DPU by using the host as an HTTP/HTTPS proxy (Squid). I’ll organize it in the correct order, explain why each step matters, and point out common pitfalls.

Architecture (what you’re doing)

Host: Has Internet access
→ runs Squid proxy on 192.168.100.1:3128

DPU / SmartNIC:
→ no direct Internet, must route all HTTP/HTTPS traffic via the host proxy

Step 1 – Verify basic network connectivity (DPU ↔ Host)

On the DPU:

ping 192.168.100.1


✔️ Must work before continuing
❌ If it fails, fix routing / interface configuration first

Step 2 – Install and configure Squid on the HOST
2.1 Install Squid
sudo apt update
sudo apt install -y squid

2.2 Configure Squid ACLs

Edit:

sudo vim /etc/squid/squid.conf


Add (or ensure):

acl dpu src 192.168.100.0/30
http_access allow dpu
http_access allow localhost


💡 Notes:

/30 covers 192.168.100.1–192.168.100.2

Order matters in Squid — allow rules must appear before any deny rules

2.3 Ensure Squid listens on the DPU-facing interface

Check for:

http_port 3128


Restart Squid:

sudo systemctl restart squid
sudo systemctl status squid


Test from host:

ss -lntp | grep 3128

Step 3 – Enable forwarding & NAT on the HOST (critical)

Without this, Squid may run but traffic won’t exit to the Internet.

3.1 Enable IP forwarding
sudo sysctl -w net.ipv4.ip_forward=1


Persist it:

echo "net.ipv4.ip_forward=1" | sudo tee /etc/sysctl.d/99-forwarding.conf

3.2 Enable NAT (MASQUERADE)

Replace eth0 with your host’s Internet interface:

sudo iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE


Verify:

sudo iptables -t nat -L -n -v

Step 4 – Configure proxy on the DPU (APT + environment)
4.1 Configure APT proxy on DPU
echo 'Acquire::http::Proxy "http://192.168.100.1:3128";' | sudo tee /etc/apt/apt.conf.d/01proxy
echo 'Acquire::https::Proxy "http://192.168.100.1:3128";' | sudo tee -a /etc/apt/apt.conf.d/01proxy


Verify:

cat /etc/apt/apt.conf.d/01proxy

4.2 Export proxy variables (for curl, wget, etc.)
export http_proxy=http://192.168.100.1:3128
export https_proxy=http://192.168.100.1:3128


(Optional persistent)

echo 'export http_proxy=http://192.168.100.1:3128' >> ~/.bashrc
echo 'export https_proxy=http://192.168.100.1:3128' >> ~/.bashrc

Step 5 – Fix DATE & TIME on the DPU (very important)

Incorrect time = TLS certificate failures.

Check:

date


Set manually (example):

sudo date -s "2025-12-07 08:19:07 UTC"


💡 Best practice (if allowed):

sudo timedatectl set-ntp false
sudo timedatectl set-time "2025-12-07 08:19:07"

Step 6 – Test Internet from the DPU
6.1 APT
sudo apt update

6.2 Curl
curl https://www.google.com

6.3 Check Squid logs (HOST)
sudo tail -f /var/log/squid/access.log


You should see requests from 192.168.100.x.

Common Problems & Fixes
Problem	Cause	Fix
TLS cert errors	Wrong DPU time	Fix date/time
Connection timeout	IP forwarding off	Enable net.ipv4.ip_forward
Squid access denied	ACL order wrong	Move http_access allow dpu up
Works for apt, not curl	Missing env vars	Export http_proxy
Squid running but no Internet	Missing NAT	Add MASQUERADE rule

Host: Install Squid

Host: Allow DPU subnet in squid.conf

Host: Enable IP forwarding + NAT

DPU: Set APT proxy

DPU: Export proxy env vars

DPU: Fix date/time

If your host uses IPv6, you still need to be clear about what traffic the DPU is actually sending. In practice, APT, curl, and most DPUs will still use IPv4 unless explicitly configured for IPv6.

Below is the correct guidance for an IPv6-capable host, covering both cases.

Key Point (important)

Squid proxying HTTP/HTTPS from the DPU does NOT require IP forwarding at all
as long as the DPU talks to Squid via TCP.

IP forwarding is only needed if:

The DPU routes non-proxy traffic through the host, or

You want the host to act as a gateway, not just a proxy

Case 1 – DPU uses Squid proxy (MOST COMMON)
✅ What you actually need

Squid listening on 192.168.100.1:3128

ACL allows DPU subnet

Host itself has Internet (IPv4 or IPv6 — doesn’t matter)

❌ What you do NOT need

net.ipv4.ip_forward=1

NAT / MASQUERADE rules

Why

The traffic flow is:

DPU ──TCP──> Squid (host) ──TCP──> Internet


Squid creates its own outbound connections using the host’s network stack (IPv4 or IPv6).

Case 2 – DPU needs full routing via host (NOT just proxy)

If you want all traffic (ICMP, raw TCP, package mirrors without proxy, etc.):

2.1 Enable IPv6 forwarding (host)
sudo sysctl -w net.ipv6.conf.all.forwarding=1


Persist it:

echo "net.ipv6.conf.all.forwarding=1" | sudo tee /etc/sysctl.d/99-ipv6-forward.conf

2.2 (Optional) IPv6 NAT – usually NOT needed

IPv6 is designed to be routed, not NATed.

Only do this if your environment requires NAT66 (rare):

ip6tables -t nat -A POSTROUTING -o eth0 -j MASQUERADE


⚠️ Most enterprise IPv6 networks do not want NAT66.

What Squid does with IPv6

Squid automatically:

Accepts IPv4 clients

Connects upstream using IPv6 if available

Falls back to IPv4 if needed

Check Squid outbound behavior:

sudo squidclient mgr:info | grep -i ip

How to verify what’s actually happening
On the DPU
curl -4 https://example.com
curl -6 https://example.com

On the host
ss -ntp | grep squid


You’ll see:

Client side: IPv4 (DPU → host)

Server side: IPv6 (host → Internet)

Recommended setup for SmartNIC / DPU
Component	Setting
DPU → Host	IPv4 (simple, stable)
Host → Internet	IPv6 (native)
Access method	Squid proxy
IP forwarding	❌ Not required
NAT	❌ Not required
Bottom line

If you’re using Squid as a proxy:

✔️ You do not need IPv4 forwarding
✔️ You do not need IPv6 forwarding
✔️ You do not need NAT

You only need forwarding if the host is acting as a router, not a proxy.
